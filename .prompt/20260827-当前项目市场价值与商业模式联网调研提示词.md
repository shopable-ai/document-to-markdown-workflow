## 一、研究目标

回答以下核心问题：

1. 这个项目解决的问题是否具有真实、持续且可付费的市场需求？
2. 现有能力中，哪些是客户愿意付费的核心价值，哪些只是工程实现细节，哪些还不能作为卖点？
3. 最适合优先切入的客户类型、使用场景、地区和行业是什么？谁使用、谁受益、谁审批、谁付钱？
4. 与国内外 Document AI、OCR、PDF/Office 转 Markdown、AI 数据接入、文档解析 API、知识库导入工具和开源解析框架相比，项目的可防御差异是什么？
5. 应优先采用哪一种商业模式：企业私有化部署、年度软件许可、按页/API 计费、托管服务、文档转换服务、开源核心版、行业解决方案，还是它们的组合？
6. 在当前成熟度下，项目的客户经济价值、可实现收入空间、技术资产价值和商业化风险分别是什么？不要在缺少用户、收入和增长数据时直接给出武断的公司估值。
7. 从“内部可运行工作流”变成“可销售产品”，最少还缺哪些产品化能力、验证证据和渠道？

## 二、项目事实基线

### 2.1 项目定位

这是一个“本地优先、证据驱动的文档资产化与 Markdown 转换工作流规格包及执行系统”。它不只是 OCR，也不只是把 PDF 文本复制为 Markdown。目标是把复杂文档转换为适合人工阅读、检索和后续 AI 使用的 Markdown，同时保留必要视觉信息、来源追溯、页面覆盖、失败证据和不确定性状态。

当前更接近可复用的工程工作流/私有化处理底座，还不是已经完成多租户、账号、计费、管理后台、公开 API 和 SLA 的成熟 SaaS。

### 2.2 当前可用或已实现的能力

1. **PDF 页面级混合转换**
   - 每页可路由为 `native-only`、`native-plus-visual` 或 `visual-only`；纯文本页避免不必要的视觉模型调用。
   - 支持原生布局提取、页面渲染、OCR/视觉补充、逐页 Markdown 生成、页面覆盖检查和最终合并。
   - 单页失败不会被总状态掩盖；最终必须核对缺页、重页、额外页、页面顺序和所需证据。

2. **PPTX 与 PDF 的确定性原生提取基础**
   - PPTX XML 解析器、PDF 布局解析器、页面渲染器和嵌入媒体读取能力已登记为 available。
   - 生产运行遵循“一次运行一个来源、一个独立输出包”的来源隔离原则。

3. **读者层与工程层双输出边界**
   - 默认交付简洁读者包：`index.md`，以及仅在 Markdown 无法替代其语义时才保留并实际引用的 `assets/`。
   - 可显式启用工程输出，保留 manifest、来源指纹、页面证据、运行报告和验收材料，便于审计、排障和复现。

4. **来源保真、状态与严格验收**
   - 支持来源 SHA-256、页码/页面标记、资产链接、来源出现记录、命名、去重和独立 validator。
   - 明确区分 `passed`、`needs-review`、`failed`、`Unknown`；文件存在、模型返回成功或局部阶段通过均不等于整包完成。
   - Markdown 语言修复受到结构守卫约束，不能静默改动图片引用、页序、原始证据或未确认关系。

5. **长任务、断点续跑与批量处理基础**
   - 长 PDF 可后台启动、查看单次状态、取消和在原运行根续跑。
   - 支持逐页持久化进度、复用已验证页面、批量 PDF 路线检测、固定批次根、严格来源级汇总和读者集合导出。
   - 通用多来源入口仍受来源隔离和阶段门约束，不能宣传为任意格式的一键无限并发平台。

6. **本地/局域网优先的模型与隐私路线**
   - 系统 OCR、局域网视觉模型页面分析、局域网语言质量修复适配器已登记为 available；当前对话的在线视觉模型只作为显式授权的可选路线。
   - 设计上适合对隐私、数据出境、成本控制或离线处理有要求的客户，但任何一次局域网模型可用性和质量仍需按真实输入验证。

7. **Markdown 质量与资产治理**
   - 包含页面单元拆分/合并、页眉页脚噪声清洗、标题和格式修复、跨页保守对账、低置信度关系保留、图片裁剪/重链、语义资产筛选与验收。
   - 可选的电子书低价值页清洗只能在完整转换之后执行，不替代来源转换和验收。

8. **独立 EPUB 原生转换能力**
   - 可从可读 EPUB 的 OPF/spine/XHTML 提取 `index.md`、引用资产及来源/转换报告。
   - 它是独立能力，不应被描述成 PDF OCR 路线的一部分。

9. **图片语料与读者资产清理能力**
   - 可审计 Markdown 读者包中的重文本图片，也支持独立图片语料模式；采用固定输入清单、逐图检查点、哈希锁定删除计划和可恢复账本。
   - 这更适合作为文档资产治理或知识库清洗的附加模块，是否能成为独立产品需要市场验证。

### 2.3 不能当作现成商业卖点的能力

1. 传统 `.ppt` 解析器和 DOCX OOXML 生产解析器仍为 `planned`。
2. “Markdown 到 GPT-image-2 单图”已有 Workflow、Skill 和验收规格，但提示词渲染器、图片供应商适配器、下载与完整性检查仍为 `planned`；不能宣传成已可交付的在线图片生成产品。
3. 下游 RAG、向量数据库、知识库问答、权限系统、协作编辑、多租户 SaaS、账号计费、公开 API、管理后台和企业 SLA 不是当前 Workflow 已交付功能。
4. 局域网模型被登记或能够连接，不等于每类真实文档都已达到生产质量；复杂版式、扫描件、表格、图示关系和中文 OCR 仍需要基准集与人工复核数据。
5. 当前项目有大量契约、守卫和测试，但这证明的是工程一致性与可审计性，不自动证明产品市场匹配、客户付费意愿或规模化交付能力。

### 2.4 可能的差异化假设——必须由市场证据检验

- 本地/局域网优先，适合敏感文档和不能直接上传公有云的客户；
- 原生解析优先、视觉模型按页升级，可能比“全量 OCR/全量大模型”更省成本；
- 不只追求非空文本，而是追求页面覆盖、来源追溯、复杂视觉保留和独立验收；
- 读者包与工程证据包分层，兼顾终端可读性与企业审计；
- 对中文文件名、复杂目录、大批量电子书/资料库、扫描页和混合图文材料有较强工程适配；
- 可恢复、失败可见、哈希锁定和 fail-closed 的处理方式，可能适合出版、档案、合规、咨询知识库和企业 AI 数据准备。

不要默认这些差异一定形成护城河；请调查客户是否愿意为它们付费，以及主流竞品是否已有同等能力。

## 三、联网研究要求

1. **必须联网搜索，且同时搜索中文与英文资料。** 以执行研究当天为截止日，优先使用最近 24 个月的信息；经典或基础资料可更早，但要标注日期。
2. **优先使用一手来源。** 包括竞品官方产品页、官方文档、官方价格页、API 定价、部署说明、安全/隐私说明、GitHub 仓库、发布说明、客户案例、招投标/采购信息和监管文件。行业报告或媒体只能作为补充。
3. **每个关键市场事实都要给出可点击 URL、来源名称、发布日期或访问日期。** 价格、产品状态和公司信息必须核对当前页面，不能依赖记忆。
4. 至少覆盖以下搜索主题：
   - Document AI、Intelligent Document Processing、OCR、visual document understanding；
   - PDF/Office/EPUB to Markdown、AI-ready document ingestion、RAG data preparation；
   - 本地部署、on-premise、air-gapped、private document processing；
   - 中文复杂文档解析、出版数字化、档案数字化、企业知识库数据治理；
   - 按页 API、企业许可、私有部署、专业服务的公开或可推断价格基准。
5. 竞品研究至少分四类，不要只列大厂：
   - 公有云 Document AI/OCR API；
   - 面向 LLM/RAG 的文档解析 API 或 SaaS；
   - 开源 PDF/文档解析框架；
   - 私有化部署、行业数字化服务商和企业自建方案。
6. 可以把 Unstructured、LlamaParse、Docling、MinerU、Marker、Mistral OCR、Azure AI Document Intelligence、Google Document AI、Amazon Textract、Adobe、AnyDoc 等作为检索种子，但必须通过当前搜索判断其实际状态，并主动寻找中国市场和垂直行业中的其他直接竞品。
7. 发现数字冲突时，列出不同口径并解释原因；没有可靠数据时写 `Unknown`，再给出获取该数据的低成本验证方法。
8. 不得把宏观“AI 市场规模”直接当作本项目 TAM。市场规模必须至少提供一个**自下而上的测算**：目标客户数 × 可实现年客单价，或年处理页数 × 可实现单页收入，并给出保守/基准/乐观三种情景。

## 四、必须完成的分析

### 4.1 功能真值与产品化差距

先制作一张表，分为：

- 当前可销售能力；
- 有工程能力但仍需真实客户验证；
- 已有规格但未完成实现；
- 明确不在当前范围。

如果我上传的项目文件与上面的摘要冲突，按以下优先级判断：

`workflow-registry.yaml` / `tool-registry.yaml` 的当前状态字段 → 对应 `workflow.yaml` 与验收契约 → 当前 README → 本提示词摘要。

任何 `planned` 项一律不能写成已实现能力。

### 4.2 客户与付费问题

针对候选细分市场，逐一说明：

- ICP（理想客户画像）；
- 典型文档、年处理量、隐私等级和错误成本；
- 使用者、业务受益者、技术把关者、预算拥有者和最终采购者；
- 当前替代方案及其成本；
- 最急迫的购买触发事件；
- 愿意付费的价值单位：每页、每份文档、每席位、每节点、每年许可、项目交付或节省的人工审核小时；
- 销售周期、集成难度、合规门槛与可复制性。

至少比较：出版/内容机构、档案与图书馆、咨询/研究机构、企业知识管理团队、AI/RAG 项目团队、教育培训资料库、专业服务或文档处理 BPO。不要默认所有行业都值得进入。

### 4.3 竞品矩阵

给出 10–20 个有代表性的直接或邻近竞品，并比较：

- 支持格式和复杂版式能力；
- 中文与扫描件能力；
- Markdown/结构化输出；
- 图片、表格、图示关系保留；
- 来源追溯、页面覆盖、失败状态和人工复核；
- API / SaaS / 私有化 / 离线部署；
- 当前公开价格或价格机制；
- 开源许可证与自建成本；
- 本项目相对优势、劣势和可被复制程度。

最后指出：真正的直接竞品是谁、最危险的免费替代品是谁、客户为什么可能仍选择人工或自建。

### 4.4 市场价值分层

不要把“市场价值”简化成一个估值数字。分别评估：

1. **客户经济价值**：节省人工、缩短入库周期、降低错误/合规风险、提高 AI 检索质量；
2. **收入潜力**：可服务客户数量、ACV、按页收入、续费和扩张空间；
3. **技术资产价值**：工作流、验收体系、边缘案例经验和私有化交付能力的替代成本；
4. **战略价值**：能否成为企业 AI 知识数据入口、集成层或行业解决方案组成部分；
5. **投资/公司价值**：只有在存在收入、客户、增长、毛利和留存数据时才给估值方法；当前缺数据时只给情景框架与需要补采的指标。

### 4.5 商业模式选择

至少比较并打分以下模式：

1. 企业私有化部署许可 + 年度维护；
2. 托管 API / 按页计费；
3. 本地团队版或桌面版年度订阅；
4. 文档转换项目服务 / BPO；
5. 开源核心版 + 企业增强版；
6. 面向一个垂直行业的端到端解决方案；
7. 与知识库/RAG 集成商、扫描服务商或模型厂商合作分销。

评分维度至少包括：付费意愿、与当前能力匹配度、初始现金流、毛利潜力、销售周期、交付成本、可规模化程度、数据隐私适配、竞争强度、护城河和 12 个月内可行性。

请明确推荐：

- 一个主商业模式；
- 一个早期现金流模式；
- 一个中长期扩张模式；
- 为什么暂时不选其他模式。

### 4.6 定价与单位经济

基于真实竞品价格和客户价值，提出人民币为主、美元为辅的价格区间。至少给出：

- 试点/PoC；
- 标准私有部署或团队版；
- 企业版；
- 可选的按页/API、人工复核和专业服务价格。

建立可修改的单位经济公式，至少包含：

- 每页原生解析、OCR、视觉模型、存储和人工复核成本；
- 不同页面路线占比；
- 部署、售前、客户成功和维护成本；
- 毛利率、回本周期和盈亏平衡客户数。

缺少真实成本时，用变量和范围，不要伪造精确数字。说明最需要实测的 5 个参数。

### 4.7 商业化路径与验证

提出 12 个月路线，但优先写关键步骤，再写细节：

- 0–30 天：需求访谈、样本收集、付费试点验证；
- 31–90 天：最窄可售产品、定价测试、首批设计合作客户；
- 3–6 个月：产品化、部署、权限、评测、交付标准；
- 6–12 个月：渠道、垂直模板、续费与扩张。

列出从当前工程工作流变成商业产品的最低补齐项，例如：安装部署、配置管理、任务队列、权限与审计、API/CLI 稳定性、UI、租户隔离、计费、监控、评测集、人工复核台、连接器、数据保留策略、备份恢复、安全文档、服务等级和客户支持。按“首单前必须有 / 10 个客户前必须有 / 规模化前必须有”排序。

设计 5–8 个低成本商业验证实验。每个实验写清：假设、对象、动作、成功指标、失败阈值、预算、周期和下一步。必须包括至少一个真实付费或付费意向实验，不能只用问卷和点赞验证。

## 五、输出格式

请用中文输出一份结构清楚、数据可复核的报告，按以下顺序：

1. 一页执行摘要：结论、推荐切口、主商业模式、最大机会、最大风险；
2. 项目功能真值表与当前产品成熟度；
3. 客户问题、ICP、购买链和优先细分市场排名；
4. 市场趋势与需求证据；
5. 国内外竞品矩阵和替代方案；
6. 差异化、护城河强度和容易被复制的部分；
7. TAM / SAM / SOM：自上而下参考 + 自下而上三情景测算；
8. 商业模式评分表与最终推荐；
9. 定价、单位经济和盈亏平衡模型；
10. 最窄可售产品定义与 12 个月路线；
11. 30/60/90 天行动计划；
12. 风险、反证、停止条件和需要补采的数据；
13. 来源附录：标题、机构、日期、URL、用于支持哪项结论。

在报告最前面明确给出以下判断，并分别标注置信度：

- **是否值得商业化：** 是 / 有条件地是 / 暂不建议；
- **最值得优先销售的产品形态：** 一句话；
- **最优先客户：** 一句话；
- **客户愿意付费的核心结果：** 一句话；
- **未来 90 天最重要的验证：** 一句话。

报告最后再给一个“决策卡”：

- 现在应该做的 3 件事；
- 现在不应该做的 3 件事；
- 3 个必须用真实客户验证的最大假设；
- 如果 90 天后仍没有哪些证据，就应暂停或改变方向。

## 六、质量约束

- 将事实、推断和建议分别标注；不要把推断写成事实。
- 不要因为项目技术复杂就自动判断有商业价值，也不要因为有开源竞品就自动判断没有商业价值。
- 不要把“支持私有化”当作万能卖点；必须找出真正因隐私、合规、成本或网络限制而付费的客户。
- 不要建议一开始同时做所有行业。必须给出一个最窄切口和明确放弃项。
- 不要用没有方法论的市场报告数字装饰答案。
- 不要把测试通过、代码量、Skill 数量或 Workflow 数量直接当成估值依据。
- 如果证据不足以支持结论，明确写 `Unknown`，说明还需要什么数据，以及如何在 30 天内获得。
- 结论必须能直接指导：是否投入、先卖给谁、卖什么、按什么方式收费、下一步验证什么。
