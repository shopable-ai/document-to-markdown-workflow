# AI 文档驱动工作流：环节宇宙

这份文档先回答“一个容易漂移的 AI 项目，究竟有哪些不同种类的问题需要被控制”。它是全局认知地图，不是第二份 Workflow 配置，也不是要求每个项目都创建一套同样多的文件。

## 1. 为什么先定义环节宇宙

AI 的错误不只发生在“生成代码”这一刻。常见漂移包括：把用户意图解释错、把候选建议当成需求、把需求直接跳成实现、把一次运行结果当成通用能力、把文件存在当成验收通过，以及修改上游后继续使用已经失效的下游证据。

因此，文档驱动不能只是一条：

```text
需求 → Spec → 代码
```

更稳妥的结构是：先把所有问题放入环节宇宙，再根据项目风险和任务类型抽取一条有依赖、有门禁、有回退的流程。宇宙层负责“不遗漏问题”，流程层负责“当前先做什么”，执行层负责“具体怎样运行”。

## 2. 五个平面

| 平面 | 负责回答 | 典型内容 | 不能替代 |
|---|---|---|---|
| 控制平面 | 谁能决定、何时能推进、何时必须停止 | 权威位置、状态、阶段门、权限、审批、声明上限 | 业务事实和代码实现 |
| 认知平面 | 我们知道什么、依据是什么、哪里未知 | Source、Fact、Assumption、Unknown、研究、意图、上下文快照 | 已批准需求和运行证明 |
| 设计平面 | 业务要怎样被表达和分解 | Scenario、Trigger、Business Chain、Capability、Function、Requirement、行为案例、架构和契约 | 执行状态和测试结果 |
| 执行平面 | 已批准的内容如何被实现和运行 | Spec、Task、Workflow、Skill、Tool、Model、预算、重试、checkpoint、fallback | 业务批准和验收裁决 |
| 证据平面 | 凭什么能声称达到某个范围 | Run、Evidence、独立 Review、Verdict、Claim、复盘、失效记录 | 上游原意和需求基线 |

五个平面可以并行产生内容，但不能互相越权。例如，执行器可以发现需求矛盾并提出变更，不能直接改写批准需求；验收器可以拒绝交付，不能替用户重新定义目标。

## 3. 环节宇宙清单

下面的清单是“可能需要控制的全部问题域”，不是一条固定顺序。每个项目按范围和风险选择其中的环节，并保留未启用环节的 `not_applicable` 理由，而不是伪造空文件。

| 编号 | 问题域 | 核心问题 | 主要平面 |
|---|---|---|---|
| U01 | 项目与来源 | 当前处理哪个项目、哪些来源、什么范围和权限？ | 控制 / 认知 |
| U02 | 原始意图 | 用户原话、背景、目标、非目标和成功指标是什么？ | 认知 |
| U03 | 事实与未知 | 哪些内容有来源，哪些是假设、冲突或 Unknown？ | 认知 |
| U04 | 样例与反例 | 什么是期望结果、允许变化和绝对不能接受的结果？ | 认知 / 证据 |
| U05 | 需求发现 | AI 发现了哪些明确需求、隐含候选、缺口和待确认问题？ | 认知 |
| U06 | 业务叙事 | 谁在什么情境下要得到什么业务结果？ | 设计 |
| U07 | 业务确认 | 哪些最小范围已经获得合法确认，哪些还只是候选？ | 控制 / 认知 |
| U08 | 场景与链路 | 正常、异常、拒绝、恢复和合法终态如何发生？ | 设计 |
| U09 | 能力与功能 | 为完成链路需要什么业务能力，用户能观察和使用什么？ | 设计 |
| U10 | 功能需求与行为 | 单个功能的触发、规则、边界、输入、输出和行为案例是什么？ | 设计 |
| U11 | 质量与风险 | 性能、成本、可用性、安全、隐私、兼容、恢复和责任边界是什么？ | 控制 / 设计 |
| U12 | 研究与决策 | 哪些未知需要研究，哪些候选方案需要比较，何时形成 ADR？ | 认知 / 设计 |
| U13 | 工程设计 | 输入输出、状态、错误、权限、组件和外部系统怎样连接？ | 设计 |
| U14 | 验收与测试空间 | 每项要求怎样被验证，边界、反例、组合和失败怎样覆盖？ | 设计 / 证据 |
| U15 | 执行投影 | 需求怎样投影为 Spec、Task、Workflow、Skill、Tool、Model 和 Context？ | 执行 |
| U16 | 运行控制 | 如何限流、暂停、重试、恢复、取消、隔离副作用和记录进度？ | 控制 / 执行 |
| U17 | 运行与证据 | 这次运行的输入、版本、环境、结果和失败是什么？ | 证据 |
| U18 | 独立审核与验收 | 谁依据哪些事前规则重新检查，结论是什么？ | 控制 / 证据 |
| U19 | 交付与声明 | 在什么来源、范围、环境和证据等级内允许声称什么？ | 证据 |
| U20 | 反馈与演进 | 错误属于哪一层，应该更新哪份文档，哪些下游需要重开？ | 控制 / 证据 |
| U21 | 时序与状态变化 | 哪些是时间先后、因果、依赖、优先、阅读或执行顺序？ | 认知 / 设计 / 执行 |
| U22 | 需求推理与对象分类 | 用户表达的是目标、需求、问题、困惑、失败还是期望结果？ | 认知 / 设计 |
| U23 | 认知负荷与重新进入 | 信息如何被选择、压缩、回源，以及如何从中断处继续？ | 认知 / 执行 |
| U24 | 知识增量与长期生命周期 | 多来源增加了什么，哪些内容冲突、过期或需要迁移？ | 认知 / 证据 |

## 4. 受控对象的六类职责

为了避免“所有内容都塞进一份 Markdown”，文档至少应分成以下六类：

1. **输入与事实**：原始来源、来源清单、Fact、Assumption、Unknown、研究材料。
2. **业务与需求**：目标、非目标、业务叙事、场景、链路、能力、功能、功能需求和需求基线。
3. **决策与设计**：方案比较、ADR、工程链路、I/O 契约、状态和质量属性。
4. **执行计划**：Spec、Acceptance、Traceability、Task、Workflow、Skill/Tool/Model/Context 映射。
5. **运行与证明**：Run、checkpoint、Evidence、AI Review、Verdict、Claim、交付说明。
6. **演进与治理**：变更请求、影响预览、失效传播、复盘、回归记录、替代和退休记录。

每个对象只有一个权威定义位置，可以被多个下游引用；派生视图可以聚合导航，但不能成为第二份可编辑真相。

## 5.1 业务需求对象的明确推导链

旧项目中的长链路仍然有价值，但它属于“业务需求对象如何逐步结构化”的推导链，不应和项目级 16 环节或单次 Workflow 的阶段编号混为一谈：

~~~text
来源材料
→ 事实 / 未知项
→ 需求对象分类与需求推理
→ 业务需求
→ 使用场景 / 触发条件
→ 业务链路
→ 业务能力
→ 业务功能
→ 功能需求
→ 决策门
→ 需求基线
→ 行为规范 / 行为案例
→〔按需：研究 / 架构决策〕
→ 工程设计 / 输入输出契约
→ 实施规格 / 工程任务 / 验收标准
→ 执行投影
→ 工作流 / 技能 / 工具 / 模型 / 上下文
→ 运行记录 / 证据
→ 独立验收结论 / 评分卡
→ 有边界的声明
→ 变更 / 失效 / 重新验证
~~~

这条链回答“一个业务意图怎样逐步变成可实现且可证明的对象”；项目主链回答“人在当前项目中现在应推进哪一组工作”；执行链回答“某次运行实际怎样执行”。三者通过有类型引用连接，不能用同一个 `completed` 状态或一份超级 Markdown 代替。

三者的区别可以简化为：**环节宇宙是问题全集，项目主链是推进导航，业务需求推导链是对象变形和追溯关系**。它们不是三条需要同时从头跑到尾的流程。

## 5.2 认知与时序是叠加层，不是新增主流程

用户提供的 J01–J18 可作为知识、学习和多来源研究任务的候选观察层。当前项目只抽取其中与实际风险相关的部分，并通过 [认知、需求推理与时序参考叠加层](COGNITIVE-REASONING-AND-TEMPORAL-OVERLAY.zh.md) 记录。它重点补足：六种用户对象的区分、需求推理的前提与替代解释、时间顺序与因果顺序的区分、边界/反例/回源，以及失败后的回环。

该叠加层默认是 `reference-candidate`，不改变 P01–P16、A1–A7 或 B1–B7 的数量。只有在真实样例、反例、来源核对和人工确认后，才允许把其中的候选结构晋升为正式契约或产品需求。

## 5. AI 特有的贯穿控制

以下规则不是可选的提示词建议，而是所有 AI 节点都应能被流程或契约检查的控制条件：

- **意图四分法**：保存 `original_intent`、`interpreted_intent`、`approved_intent` 和 `implementation_intent`，防止“实现正确但目标错误”。
- **上下文可重放**：记录本次实际纳入、排除和截断的文件、hash、权威状态、顺序和理由；聊天与临时提示词不能自动获得批准权威。
- **事实分层**：来源原文、AI 候选、人工确认、实现建议和运行结果不能混成同一字段。
- **Unknown 真实保留**：无法由当前证据确认的文字、关系、权限、指标或责任不补猜；Unknown 必须有 owner、影响、阻断性和处理入口。
- **生成与审核分离**：生成节点不能给自己的输出签发独立通过；审核必须引用明确规则、对象位置和 Evidence。
- **候选不升格**：模型、工具、架构和业务解释可以是候选，但没有决策证据不能进入 active Spec 或生产声明。
- **预算与失败出口**：每个模型/Agent 节点声明输入输出 Schema、预算、重试、超时、fallback、能力损失和声明封顶。
- **禁止静默改写**：需求、原始来源、历史 Run 和历史 Evidence 不原地覆盖；修复必须产生新版本或新 attempt。

## 6. 从宇宙抽取流程的原则

抽取流程时依次问四个问题：

1. 本次任务的目标、来源、风险和不可逆副作用是什么？
2. 哪些环节是当前任务的前置条件，哪些可以并行，哪些只是条件启用？
3. 每个环节的输入、输出、停止条件、失败状态和证据出口是什么？
4. 出错后应回到哪一个最早责任环节，而不是继续在下游打补丁？

当前项目据此抽取出一条 16 环节的人类导航；A1–A7、B1–B7 仍然是其中的执行投影。机器读取顺序见 [document-driven-workflow.yaml](contracts/document-driven-workflow.yaml)，人类推进顺序见 [PROJECT-DELIVERY-WORKFLOW.zh.md](PROJECT-DELIVERY-WORKFLOW.zh.md)，错误定位和变更回写见 [ARTIFACT-AND-CHANGE-GOVERNANCE.zh.md](ARTIFACT-AND-CHANGE-GOVERNANCE.zh.md)。
