# 认知、需求推理与时序参考叠加层

> 状态：`reference-candidate`
> 权威级别：非规范、非自动路由
> 用途：为需要理解用户、资料和复杂行为的项目提供可启用的推理框架。

这份文档吸收用户提供的“用户旅程、需求与高频问题现象宇宙”中的部分结构，但不把参考页面直接升级为事实、需求、Workflow 或产品功能。它解决的是三个容易被混淆的问题：用户到底在表达什么、事件到底怎样发生、AI 的推断凭什么成立。

## 1. 六种对象必须分开

同一句用户原话可以同时包含多种对象，AI 先分类，不能直接把它改写成需求：

| 对象 | 需要回答 | 示例 |
|---|---|---|
| 用户目标 | 用户最终想达到什么？ | 我要学会做决策 |
| 用户需求 | 为达到目标需要什么支持？ | 我需要高质量案例练习 |
| 用户问题 | 用户在哪个任务上做不好？ | 我只会复述，不会迁移 |
| 用户困惑 | 哪个概念、关系或判断不清楚？ | 为什么两个专家说法相反？ |
| 失败现象 | 已经发生了什么可观察失败？ | 执行三次都失败 |
| 期望结果 | 什么结果算改善或成功？ | 能识别何时该用哪个方法 |

对象之间可以形成候选推导，但推导不是事实：

~~~text
用户原话 / Source
→ 对象分类
→ 事实、例子、失败和 Unknown 分离
→ 候选需求推理
→ 人工确认
→ Business Requirement
~~~

## 2. 需求推理记录

P04 的“AI 需求发现”至少应能留下以下记录，而不是只输出一段流畅的需求叙事：

| 字段 | 含义 |
|---|---|
| `statement_ref` | 原话、来源片段、事件或运行证据的位置 |
| `object_type` | 六种对象之一，可为多个候选并标注主次 |
| `observed_facts` | 直接可见、可回源的内容 |
| `inference` | AI 推导出的目标、约束、需求或风险 |
| `alternatives` | 仍然成立的其他解释 |
| `confidence` | 推理置信度，不等于需求批准状态 |
| `unknowns` | 尚不能确认的事实、条件和责任 |
| `decision_impact` | 未确认时会阻断或改变什么 |
| `confirmation_owner` | 谁能确认或否定该推理 |
| `promotion_status` | `candidate`、`confirmed`、`rejected`、`unknown` |

只有 `confirmed` 的候选，且确认范围、版本和证据可回放时，才允许进入 `Business Requirement` 或下游基线。`confidence=high` 不能替代 `promotion_status=confirmed`。

每条推理记录还应带 `reasoning_id`、`subject_ref`、`role_ref`、`host_stage_id`、`derived_from`、`promotes_to`、`blocks` 和 `resolved_by`；这些字段用于建立关系，不代表 AI 获得自动批准权。

## 3. 时序推理不是一个普通的步骤

“时序”至少包含六种不同顺序，不能把它们混为一张箭头图：

| 顺序类型 | 说明 | 证据要求 |
|---|---|---|
| 时间顺序 | A 在 B 之前或之后发生 | 日志、原文、时间戳或明确叙述 |
| 因果顺序 | A 导致、阻止或改变 B | 除先后外还需要机制或对照证据 |
| 依赖顺序 | B 必须等待 A 的结果 | 契约、前置条件或状态约束 |
| 优先顺序 | 当前先处理 A，再处理 B | 目标、风险、资源或决策规则 |
| 阅读顺序 | 为了理解而推荐 A→B | 认知负荷、概念依赖或用户目标 |
| 执行顺序 | 系统实际按 A→B 运行 | Workflow、Run 和 checkpoint |

时序案例建议最少包含：

~~~yaml
temporal_case:
  trigger: "触发事件"
  preconditions: []
  events:
    - id: E01
      actor: "谁或哪个节点"
      action: "做了什么"
      input: []
      output: []
      observed_order: 1
      relation: observed  # observed | inferred | unknown
  decision_points: []
  branches: []
  recovery: []
  terminal_states: []
  unknowns: []
~~~

完整的事件、状态、关系、因果证据和失败回退要求见 [temporal-case.yaml](contracts/temporal-case.yaml)。上面的示例只是人类理解用的最小轮廓，不是可以省略证据的简化格式。

硬规则：仅凭“先发生”不得生成“因此导致”；无法确认的顺序、条件或因果必须保留 `Unknown`。如果运行失败，至少区分“方法错误、前置条件不满足、执行错误、输入变化、验收规则错误”五种候选原因，再决定回退环节。

## 4. 用户认知生命周期：候选 J01–J18

以下 18 个阶段只作为知识、学习和多来源研究任务的可选观察层，不新增当前项目的 P01–P16，也不要求每次转换都创建 18 份文件。它允许跳转、回环和重新进入。

| 阶段 | 候选问题 | 可观察产物 |
|---|---|---|
| J01 | 为什么现在触发？真实目标是什么？ | 触发与目标记录 |
| J02 | 需要本人学习、查询、委托还是直接行动？ | 处理模式判断 |
| J03 | 缺少哪个领域、概念或能力？ | 知识缺口 |
| J04 | 去哪里发现和收集资料？ | 来源候选集 |
| J05 | 哪些资料先处理？ | 优先级与筛选理由 |
| J06 | 读前价值多大、处理多深？ | 处理深度与预算 |
| J07 | 如何建立阅读地图并在中断后重新进入？ | 地图、checkpoint、入口 |
| J08 | 怎样降低不必要的认知负荷？ | 阅读/展示负荷记录 |
| J09 | 概念、论证和关系怎样成立？ | 概念关系与论证链 |
| J10 | 哪些内容需要保留和压缩？ | 摘要、重点、压缩损失 |
| J11 | 怎样记录并回到原始来源？ | 笔记、回源指针 |
| J12 | 内容可靠到什么程度？ | 来源、证据、可靠性判断 |
| J13 | 在哪些条件下成立，何时失效？ | 边界、冲突、反例 |
| J14 | 多来源有什么重复、冲突和新增？ | 去重、冲突与知识增量 |
| J15 | 与当前项目、个人目标和判断如何连接？ | 相关性与应用判断 |
| J16 | 能否记忆、练习和迁移？ | 主动回忆、练习、迁移证据 |
| J17 | 行动后发生什么，如何调整？ | 行动反馈与回退 |
| J18 | 如何长期调用、更新和退休？ | 版本、过期、生命周期 |

参考页面中最值得保留的不是“18”这个数字，而是回环关系：执行失败可以回到 J13 检查边界，证据不足可以回到 J04 重新找资料，内容过期可以回到 J04–J14 重新收集和综合。

## 5. 映射到当前项目

| 认知/推理层 | 当前项目的承载位置 | 启用条件 |
|---|---|---|
| 需求对象分类与推理 | P02、P04、P05、P06 | 出现用户原话、隐含需求或解释分歧 |
| 时间/因果/依赖案例 | P07、P09、P10、P11、P13、P14 | 存在多节点、状态变化、恢复或顺序敏感行为 |
| 阅读地图与重新进入 | P11、P13、P14 | 长文档、批量来源或可中断运行 |
| 认知负荷与压缩 | P07、P10、A4、A5 | 结果面向人阅读，且存在摘要、重组或视觉解释 |
| 回源、证据、边界、反例 | P02、P03、P07、P13、P14、P15 | 需要可审计结论或失败可解释性 |
| 多来源综合与长期更新 | P01、P08、P16 | 来源集合、版本变化或知识库维护 |

映射只是投影关系，不是把 J 阶段硬塞进 P 阶段。当前文档转 Markdown 任务通常只需启用其中一部分；没有实际知识学习目标时，J02、J16 等可以记录 `not_applicable`。

## 6. 晋升和回退规则

1. 参考页面、用户原话和 AI 解释默认都是 `candidate`，除非有独立证据和合法确认。
2. 需求推理必须保留前提、替代解释、Unknown、责任人和影响，不得只保留结论。
3. 时序图必须区分观察到的先后、推断的因果和执行器要求的依赖。
4. 任何“总结”都要声明是否可能丢失条件、边界、证据和作者原意；不能把高压缩等同于高保真。
5. 新发现应回写最早责任文档，并使受影响的下游 Evidence 变为 stale 或重新验收；不能只修改临时 Prompt。
6. 只有经过真实样例、反例、来源核对和人工确认，参考叠加层才可以晋升为正式合同、Workflow、Skill 或产品需求。
