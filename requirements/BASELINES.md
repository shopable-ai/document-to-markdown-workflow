# 文档资产化项目三次基线

这份文件回答的是：AI 起草之后，人到底在什么地方确认什么，确认之后又允许 AI 继续到哪里。

三次基线不是形式化签字动作，而是防止三类常见漂移：

- AI 把自己的推断自动升格为已确认需求；
- 工程实现反过来定义前期业务语义；
- Run 成功、测试通过或历史评分被误当成最终验收。

## V1 业务范围基线

V1 的目标是先把“我们究竟在做什么、没在做什么”钉住。

V1 至少要确认这些问题：

- 当前直接交付是否仍然是“一个当前来源对应一个独立 Markdown 包”；
- 谁是主要读者、复核者、执行者和验收者；
- 当前范围和非目标是否写对了；
- 22 条需求里，哪些确认、哪些要改、哪些应删除；
- 复杂视觉、模型授权、多格式候选和可选下游是否在当前范围内；
- 哪些 Unknown 会阻断继续展开。

V1 通过后，AI 才可以继续展开：

- 场景；
- 业务链路；
- 功能；
- 行为；
- 验收方向。

V1 未通过时，AI 仍可继续整理表述，但不得进入正式工程设计。

## V2 完整需求基线

V2 的目标是把“系统应该怎样表现、哪些边界不能越过”钉住。

V2 至少要确认这些问题：

- 每个功能是否都能回指已确认需求和场景；
- 正常、边界、拒绝、异常、恢复和 Unknown 行为是否都可定位；
- 简单/复杂视觉、多格式候选、页面阶段门和独立验收边界是否已明确；
- 质量、权限、隐私、安全、恢复、状态、时序和因果边界是否已写清；
- 验收判据和测试空间是否真的能判断通过或失败。

V2 通过后，AI 才可以进入：

- 方案比较；
- 架构设计；
- 验证设计。

V2 未通过时：

- discovery 仍可作为参考保留；
- design/ 只能作为 Brownfield candidate；
- 不得生成正式 Spec、Task、Workflow、代码任务或执行路线结论。

## V3 架构基线

V3 的目标是把“怎样实现、怎样验证”钉住，而且证明它消费的是 V2，而不是偷拿现有实现当前提。

V3 至少要确认这些问题：

- 方案选择是否来自已确认需求；
- 系统边界、关键组件和 I/O 是否清楚；
- Data、State、Permission、Error 和 Quality Realization 是否完整；
- Verification Design 是否真正在消费前面的验收要求；
- 是否仍然保留了工程投影不能反向改写需求的边界。

V3 通过后，AI 才可以生成：

- 正式 Spec；
- 工程任务；
- Workflow 投影；
- 后续实现与验证执行面。

| V3 | blocked-by-V2 | V2 还没过；设计仍只是候选投影 | 保留 Brownfield 候选，不升格为正式架构 |

## 每次确认记录至少要写什么

一次合法的基线记录，至少要说明：

- `baseline_id`
- `baseline_version`
- `input_refs_and_hashes`
- `included_ids`
- `excluded_ids`
- `blocking_unknowns`
- `confirmed_by`
- `confirmed_at`
- `supersedes`
- `status`

如果缺少这些字段，就不能把一次“看过了”当成正式基线通过。

## 人工确认时应该重点看什么

### 看 V1 时

- 目标有没有被 AI 偷换成实现目标；
- 非目标有没有被偷偷写进范围；
- Unknown 有没有被假装解决。

### 看 V2 时

- 场景、功能、行为和验收能否让人判断 AI 理解是否正确；
- “先发生”是否被误写成“导致”；
- 是否已经出现没有来源的工程任务影子。

### 看 V3 时

- 设计是否真的消费 V2；
- 有没有把现有 Workflow、代码、测试或历史 Run 反向写成需求依据；
- 验证设计是否独立于实现自证。

## 当前阶段提醒

- 当前没有 confirmed 的 V1、V2 或 V3 记录。
- 静态测试、目录存在、历史评分较高，都不能替代人工基线。
- 在 V2/V3 没过之前，任何设计、Contract、Workflow 或实现都只能算候选或 Brownfield 对账，不算正式批准结果。
