# 文档资产化功能说明

> **Brownfield 参考：** 当前尚未通过 V1，本文件不能作为 C12—C14 的当前业务权威。当前中文业务入口见[项目需求说明](../项目需求/说明.md)。

这份文件写给人看。它回答的不是“脚本怎么调、字段怎么填”，而是“人在什么情况下需要这个能力，系统应该怎样表现，哪些结果不能冒充完成”。

稳定 ID 只用于追溯和讨论，不要求参与者理解工程 schema。

## 先看这 12 个功能

| 功能 ID | 功能名称 | 谁会关心 | 主要解决的问题 | 当前状态 |
|---|---|---|---|---|
| FUN-DOC-001 | 把当前来源转换成独立 Markdown | 读者、执行者 | 结果是否真的只讲当前文件，而且能脱离原文件阅读 | draft |
| FUN-DOC-002 | 尽量保留原文内容和关系 | 读者、复核者 | 文字、结构和可确认关系是否被遗漏或改写 | draft |
| FUN-DOC-003 | 让复杂图文问题可见并可纠正 | 复核者、读者 | 图文问题能否被发现、解释和修正 | draft |
| FUN-DOC-004 | 区分候选来源而不误合并 | 执行者、复核者 | 相似文件是否被错误混成同一份材料 | draft |
| FUN-DOC-005 | 如实表达结果边界 | 读者、验收者 | 人能否看懂什么已确认、什么还不能用 | draft |
| FUN-DOC-006 | 分离读者标题与来源追溯 | 读者、复核者 | 正文是否被文件名、页码和哈希污染 | draft |
| FUN-DOC-007 | 使用可验证的识别和视觉复核路线 | 执行者、复核者 | 路线选择是否真的基于质量和授权，而不是连通性 | draft |
| FUN-DOC-008 | 提取必要图片并先成功再降本 | 执行者、复核者 | 图片资产是否完整、可核对、可比较路线质量 | draft |
| FUN-DOC-009 | 生成可携带的读者图片资产 | 读者、复核者 | 图片复制后是否仍可读，且不带工程噪声 | draft |
| FUN-DOC-010 | 让长任务可观察、可停止、可恢复 | 执行者、验收者 | 长时间处理是否还能被人掌控 | draft |
| FUN-DOC-011 | 页面修复按阶段放大 | 执行者、复核者 | 是否先小范围证明，再扩大处理范围 | draft |
| FUN-DOC-012 | 在完整汇合后清洗知识库工作副本 | 下游使用者、执行者 | 低价值页是否只在后置阶段、可审计地处理 | draft-optional |

## 能力视角

这些能力不是新的权威对象，只是帮助人快速理解 12 个功能主要分成哪几类。

| 能力 | 主要回答什么问题 | 覆盖功能 |
|---|---|---|
| 当前来源正确性 | 结果是否真的只讲当前文件，候选来源是否被正确区分 | FUN-DOC-001、FUN-DOC-004 |
| 内容与关系保真 | 文字、结构、图文关系是否被保留，并且问题可见 | FUN-DOC-002、FUN-DOC-003 |
| 读者层可读与可携带 | 标题、图片和结果边界是否适合人直接阅读与转移 | FUN-DOC-005、FUN-DOC-006、FUN-DOC-009 |
| 路线与资产治理 | 识别路线、图片提取和质量/成本比较是否受控 | FUN-DOC-007、FUN-DOC-008 |
| 受控运行与后置处理 | 长任务、页面修复和可选下游是否按阶段门推进 | FUN-DOC-010、FUN-DOC-011、FUN-DOC-012 |

## A. 先保证“讲的是当前文件”

### FUN-DOC-001 把当前来源转换成独立 Markdown

谁在什么情况下使用：

- 当用户明确给出一个来源、页码或范围时。

希望完成什么：

- 产出的 Markdown 只讲当前来源。
- 读者不需要重新打开原始 PDF、PPTX 或图片，仍能读懂主要内容。

正常情况下会发生什么：

- 系统只使用当前来源和当前授权范围内的内容。
- 纯文本内容直接进入 Markdown。
- 必要的复杂视觉证据随包保存，并由正文实际引用。

异常时人会看到什么、怎样处理：

- 如果来源不清、范围冲突、或旧内容污染了当前结果，就不能给出 `passed`。
- 人应回到来源确认，而不是继续补写内容。

明确不包含什么：

- 自动找另一份相似文件来补内容。
- 用旧示例、fixture 或历史结果补齐当前文件没有的答案。
- 把“生成了一个文件”冒充成“已完成交付”。

来源于哪些需求和场景：

- 需求：REQ-DOC-001、REQ-DOC-002、REQ-DOC-022
- 场景：SCN-DOC-001
- 原始来源：TASK-TREE 第 5 节第一项

### FUN-DOC-004 区分候选来源而不误合并

谁在什么情况下使用：

- 当本次输入里出现多个可能相关的 PDF、PPTX 或其他来源时。

希望完成什么：

- 分清它们是同一逻辑材料的候选版本，还是本应分开的不同来源。

正常情况下会发生什么：

- 系统会保留差异，并要求显式判断 `same` 还是 `separate`。
- 只有在规则和人工判断都支持时，才进入候选比较。

异常时人会看到什么、怎样处理：

- 如果名字过短、关系不明、内容冲突，就保持分开或标记 `needs-review`。
- 人需要直接确认候选关系，而不是让实现层静默选择。

明确不包含什么：

- 仅凭文件名相似、扩展名相似或历史经验自动合并。

来源于哪些需求和场景：

- 需求：REQ-DOC-001、REQ-DOC-008、REQ-DOC-012
- 场景：SCN-DOC-002
- 原始来源：TASK-TREE 第 5 节第四项

## B. 再保证“内容和关系没有被改坏”

### FUN-DOC-002 尽量保留原文内容和关系

谁在什么情况下使用：

- 当来源中含有文字、数字、表格、层级、分区或可确认关系时。

希望完成什么：

- 人读到的 Markdown 能尽量保留原来的内容和结构，不因整理而改义。

正常情况下会发生什么：

- 保留文字、数字、章节、列表、表格和能确认的关系。
- 允许轻度整理标点、段落、标题层级和列表形式，但不改变条件、范围和结论。

异常时人会看到什么、怎样处理：

- 如果关系证据不足，就明确留下 `Unknown`，而不是为了完整去猜。
- 如果整理会改变原意，应保留原表达并标出问题。

明确不包含什么：

- 总结、翻译、扩写、跨来源补全。
- 把 run 顺序或实现顺序误写成业务关系。

来源于哪些需求和场景：

- 需求：REQ-DOC-003、REQ-DOC-004、REQ-DOC-012
- 场景：SCN-DOC-001、SCN-DOC-004
- 原始来源：TASK-TREE 第 5 节第二项

### FUN-DOC-003 让复杂图文问题可见并可纠正

谁在什么情况下使用：

- 当页面意义依赖布局、箭头、颜色、层级、图例或图形组合时。

希望完成什么：

- 问题不被隐藏，复核者能看见错位、遮挡、遗漏和关系未决点，并知道怎么回查。

正常情况下会发生什么：

- 可搜索的 Markdown 和可核对的视觉证据会同时存在。
- 问题、修复依据和仍未确认的部分会被分别表达。

异常时人会看到什么、怎样处理：

- 如果原图不能保存、裁切不够、或证据不足，就应保留 `needs-review` 或 `structured-only`，而不是强行写成确定答案。
- 人可以扩大证据范围或直接复核当前页/区域。

明确不包含什么：

- 用重绘图冒充来源图。
- 用“识别出了图片里的字”证明空间关系已经正确理解。

来源于哪些需求和场景：

- 需求：REQ-DOC-006、REQ-DOC-007、REQ-DOC-012、REQ-DOC-014
- 场景：SCN-DOC-003
- 原始来源：TASK-TREE 第 5 节第三项

## C. 让读者层可读，而不是被工程噪声污染

### FUN-DOC-005 如实表达结果边界

谁在什么情况下使用：

- 当需要告诉人“哪些内容可用、哪些还需复核、哪些失败了”时。

希望完成什么：

- 读者和验收者能分清 `passed`、`needs-review`、`failed` 的真正含义。

正常情况下会发生什么：

- 已确认内容、未决项、失败和证据边界会分开表达。
- 结果说明会告诉人为什么当前结论只能到这个边界。

异常时人会看到什么、怎样处理：

- 如果缺少 owner、影响范围或解决入口，就不能声称完成。
- 人需要回到最早出问题的需求、功能、行为或验收层补证据。

明确不包含什么：

- 让 runner 自报状态替代独立 Verdict。
- 把历史成功、静态测试或单次 Run 外推成当前业务验收。

来源于哪些需求和场景：

- 需求：REQ-DOC-007、REQ-DOC-012、REQ-DOC-018
- 场景：SCN-DOC-001、SCN-DOC-005
- 原始来源：TASK-TREE 第 5 节第五项

### FUN-DOC-006 分离读者标题与来源追溯

谁在什么情况下使用：

- 当系统需要给页面、章节或内容单元命名时。

希望完成什么：

- 读者层只看到语义标题；页码、文件名、哈希和对象定位留在追溯层。

正常情况下会发生什么：

- 有语义标题时，正文只呈现主题本身。
- 没有可确认标题时，允许用临时标题，但要明确标为待复核。

异常时人会看到什么、怎样处理：

- 如果标题仍被工程字段污染，人应直接改回自然语言标题。
- 如果暂时没有合适标题，就保留临时标题，不装成已确认。

明确不包含什么：

- 为了追溯方便，把来源字段写进每个标题前缀。

来源于哪些需求和场景：

- 需求：REQ-DOC-009、REQ-DOC-011、REQ-DOC-017
- 场景：SCN-DOC-001
- 原始来源：TASK-TREE 第 5 节第六项

### FUN-DOC-009 生成可携带的读者图片资产

谁在什么情况下使用：

- 当正文确实需要保留图片来表达复杂视觉语义时。

希望完成什么：

- 图片跟随 Markdown 一起移动时仍可阅读，并且文件名对读者友好。

正常情况下会发生什么：

- 只保留正文实际引用的图片。
- 用尽量简短稳定的语义名保存图片。
- 追溯字段进入 manifest 或证据层，不污染读者层名字。

异常时人会看到什么、怎样处理：

- 如果图片未被正文引用、命名冲突未处理、或名字全是页码/哈希，说明读者层还没整理好。
- 人应修正文案引用或命名规则，而不是补更多工程字段。

明确不包含什么：

- 把所有工程渲染图批量塞进读者资产包。

来源于哪些需求和场景：

- 需求：REQ-DOC-002、REQ-DOC-009、REQ-DOC-010、REQ-DOC-011、REQ-DOC-017
- 场景：SCN-DOC-003
- 原始来源：TASK-TREE 第 5 节第九项

## D. 让识别、视觉和运行受控，而不是“看起来能跑”

### FUN-DOC-007 使用可验证的识别和视觉复核路线

谁在什么情况下使用：

- 当原生提取不足，需要 OCR 或视觉模型辅助时。

希望完成什么：

- 路线选择建立在同输入、同质量维度、同授权边界之上。

正常情况下会发生什么：

- 不同路线会在相同页面集上比较文字、结构、关系、重复性、耗时、资源和成本。
- 当前证据不足时，路线保持候选，不自动升格为默认。

异常时人会看到什么、怎样处理：

- 未授权、不可用、质量不足时，应明确写成 `unavailable`、`failed` 或 `needs-review`。
- 人需要重新确认授权、路线基准或质量门，而不是把 HTTP 200 当通过。

明确不包含什么：

- 按模型列表、连通性、队列接收或参数多少来决定路线优先级。

来源于哪些需求和场景：

- 需求：REQ-DOC-013、REQ-DOC-014、REQ-DOC-021
- 场景：SCN-DOC-006
- 原始来源：TASK-TREE 第 5 节第七项

### FUN-DOC-008 提取必要图片并先成功再降本

谁在什么情况下使用：

- 当来源中存在复杂图示、嵌入图片、区域图或读者必须核对的视觉内容时。

希望完成什么：

- 先获得足够好的视觉资产和解释，再讨论是否可以降本或换默认路线。

正常情况下会发生什么：

- 不同来源格式会采用合适的提取方式形成候选。
- 复杂视觉既保留图片，也整理成可搜索 Markdown。
- 同一输入上的高质量路线可以作为比较基准。

异常时人会看到什么、怎样处理：

- 如果资产不完整、裁切不充分或质量门没过，就只能停在 `needs-review` 或 `failed`。
- 人应先修复提取、裁切、证据或路线，而不是提前做成本优化。

明确不包含什么：

- 把“提取图片”和“理解图片”混成一步。
- 还没成功就默认切到便宜路线。

来源于哪些需求和场景：

- 需求：REQ-DOC-005、REQ-DOC-006、REQ-DOC-010、REQ-DOC-013、REQ-DOC-014、REQ-DOC-021
- 场景：SCN-DOC-003、SCN-DOC-006
- 原始来源：TASK-TREE 第 5 节第八项

### FUN-DOC-010 让长任务可观察、可停止、可恢复

谁在什么情况下使用：

- 当处理超过短对话时长，或需要多页、多阶段推进时。

希望完成什么：

- 人能知道当前做到哪里、为什么停下、如何继续，而不是只能等待最终结果。

正常情况下会发生什么：

- 当前页、阶段、状态、停止点、恢复点和下一步都会有可读记录。
- 取消、失败和恢复会被明确区分。

异常时人会看到什么、怎样处理：

- 如果只看到“仍在运行”而没有当前快照、失败理由或恢复入口，说明运行控制不足。
- 人应回到运行控制规则补齐 checkpoint 和状态表达。

明确不包含什么：

- 用周期性闲聊式进度刷屏代替正式进度记录。

来源于哪些需求和场景：

- 需求：REQ-DOC-015、REQ-DOC-017、REQ-DOC-018
- 场景：SCN-DOC-005
- 原始来源：TASK-TREE 第 5 节第十项

### FUN-DOC-011 页面修复按阶段放大

谁在什么情况下使用：

- 当已有页面单元需要进行读者层 Markdown 修复时。

希望完成什么：

- 先在最小范围证明可行，再扩大，不让全量修复掩盖局部错误。

正常情况下会发生什么：

- 先第 1 页，再第 2–5 页，人工复核通过后才允许更大范围。
- 原始 OCR、页面图、Vision JSON 和 manifest 保持只读。

异常时人会看到什么、怎样处理：

- 如果前一门没过却继续扩大，或者修复覆盖了原始证据，就应立即停止。
- 人需要回到当前阶段重新检查，而不是继续批量推进。

明确不包含什么：

- 一次性全量修复替代阶段门。

来源于哪些需求和场景：

- 需求：REQ-DOC-004、REQ-DOC-012、REQ-DOC-016、REQ-DOC-017
- 场景：SCN-DOC-004
- 原始来源：TASK-TREE 第 5 节第十一项

## E. 可选后置能力

### FUN-DOC-012 在完整汇合后清洗知识库工作副本

谁在什么情况下使用：

- 当用户明确要求把已验收结果导入知识库，并希望去掉低价值整页时。

希望完成什么：

- 只在完整汇合后、可审计地处理工作副本，不破坏来源转换结果和历史证据。

正常情况下会发生什么：

- 先做哈希锁定预览，再按计划删除候选整页，然后重建索引。
- 原 PDF、原页面图、原 OCR/Vision 证据和原验收状态继续保留。

异常时人会看到什么、怎样处理：

- 如果页面数量、哈希或完整集合发生变化，就不能继续按旧计划删除。
- 人需要重新生成计划，而不是套用“每本书都删前 N 页”的规则。

明确不包含什么：

- 在来源转换尚未完整汇合前提前清洗。
- 让下游清洗结果反向定义来源转换需求。

来源于哪些需求和场景：

- 需求：REQ-DOC-019
- 场景：SCN-DOC-007
- 原始来源：TASK-TREE 第 5 节第十二项
