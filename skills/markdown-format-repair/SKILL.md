# Markdown 文档整理与修复

## 使用范围与路由

- 对独立、完整、需要直接交付的 Markdown 文档，执行本文件的全部规则。
- 对本项目 Workflow 中的 `page-unit`、`document-temp.md` 或 `index.md` 原位修复，先读取
  [`references/workflow-page-unit-boundaries.zh.md`](references/workflow-page-unit-boundaries.zh.md)。
  该参考中的页面标记、图片位置、证据边界和输出路径规则优先于下方完整文档交付规则。
- 只处理用户明确提供的文件与范围；不要自动读取同目录中的其他页面、来源证据或历史输出。

## 任务目标

整理并修复用户提供的 Markdown 文件。

目标不是重新创作、总结或改写正文，而是在**尽量保持原文内容完整、原意不变、图片引用不变**的前提下，修复 Markdown 的标题层级、排版、OCR / 转换错误、表格、错误换行、页眉页脚等问题，并最终输出一个可以直接阅读和下载的 `.md` 文件。

---

# 一、核心原则

1. **以语义为准，不机械沿用原 Markdown 格式。**
2. **不总结、不压缩、不重写正文。**
3. **不随意删除原始正文。**
4. **所有 Markdown 图片引用必须完整保留，图片路径不得修改。**
5. **不确定是否属于错误时，优先保留原文。**
6. **如果原文为繁体中文，应统一转换为简体中文。**
   - 只进行繁体 → 简体转换；
   - 不借机改写句子；
   - 专有名词、书名、人名等按正常简体中文习惯处理；
   - 英文、数字、公式、代码、URL、图片路径不要因为简繁转换而被修改。
7. **必须区分“Markdown 结构”与“正文里出现的 Markdown 字符”。**
   - `#`、`##`、`###` 只有在确实承担文档标题结构时，才能作为标题；
   - 代码、终端输出、模型日志、提示词示例、JSON、配置、算法伪代码中的 `#` / `##` / `###` 属于字面内容，不得参与标题层级；
   - 不能只用正则扫描 `^#` 后就把所有命中行当标题。
8. **先判断“前置内容 / 正文 / 附录与资料”，再决定标题样式。**
   - 出版信息、CIP、推荐序、序言、前言、致谢、作者/译者介绍等前置内容，不得与正文章节使用同一个 `##` 层级。

# 二、标题与层级修复

## 1. 按语义重新判断标题层级

不要机械沿用原文件中的 `#`、`##`、`###`、`####`。

推荐层级：

- `#`：整本书 / 整个文档的书名，只使用一次；
- `##`：**正文的主要章节**，优先用于“第 N 章”等真正章节；
- `###`：章节内部的重要小节；
- `####`：三级标题下面的细分内容；
- 更深层级只有在确实存在从属关系时才使用。

### 前置内容的特殊规则

以下内容通常属于**正文之前的前置资料**，不要机械设为 `##`：

- 图书在版编目（CIP）数据；
- 出版发行 / 版权信息；
- 推荐序、序言、前言、中文版序；
- 行业推荐、名家推荐；
- 目标读者、阅读说明、本书约定；
- 关于作者、译者、评审员；
- 致谢、献词等。

推荐处理方式：

- 保留内容；
- 这些标题优先改为 `**加粗标签**`，而不是与“第 N 章”并列的 `##`；
- 如果书籍本身存在明确的“前言 / 序章”且它确实属于正文结构，才根据原书语义决定是否作为正式标题；
- “第 N 部分 / Part N”若只是章节分组提示，可用 `**第 N 部分：……**` 作为分隔标签，让 `##` 专门保留给章节；若原书明确把 Part 作为正式可导航层级，则需整体重排正文层级，不能让 Part 与 Chapter 同级。

必须注意：

- **书名和内部章节不能使用相同层级。**
- 避免明显的标题跳级，例如 `##` 后直接出现 `####`。
- 如果原文件标题符号数量明显错误，应根据内容关系重新调整。
- 不要因为某一页视觉字号较大，就自动判断为更高层级，必须结合上下文语义。

## 2. 合并被错误拆开的页面标题

错误示例：

```md
## 走近博弈论

### 博弈的构成要素
```

修复后示例：

```md
## 走近博弈论：博弈的构成要素
```

判断原则：

- 第一行通常是章节编号 / 章节名；
- 第二行通常是当前页面主题；
- 两者组合后语义更完整；
- 第二行下面没有多个同级子主题需要继续展开。

**不要机械合并所有连续的 `## + ###`。**

如果 `###` 确实是章节内部独立小节，则应保留原有从属关系。

## 3. 处理跨页重复章节标题

如果同一章节跨越多页，每页都重复相同章节名，但每页实际主题不同，可以整理成下面这样的结果：

示例一：

```md
## 重复博弈：天长地久的聪明策略
```

示例二：

```md
## 重复博弈：为什么不带剑的契约必然无效
```

避免大量连续页面只出现完全相同的标题，影响阅读和搜索。

# 三、正文与排版修复

## 4. 修复错误换行

OCR / PDF / PPT 转换后，常出现一句话被错误拆成多行。

需要根据语义判断：

- 本来属于一句话的内容 → 合并为正常句子；
- 本来属于一个段落的内容 → 恢复为正常段落；
- 本来属于列表、步骤、关系结构的内容 → 整理成 Markdown 列表；
- 不要机械把所有短行合并。

重点保证：

- 阅读自然；
- 原意不变；
- Markdown 渲染正常。

## 5. 修复列表与缩进

检查并修复：

- 无序列表 `-`；
- 有序列表 `1.`；
- 多级列表；
- 列表缩进；
- 列表与正文之间的空行；
- OCR 导致的层级错乱；
- 孤立的缩进行；
- 本应从属于上一条内容却被拆平的项目。

应根据语义恢复合理层级，而不是只按空格数量处理。

## 6. 保护代码、日志、终端输出和提示词中的 Markdown 字符

这是电子书转换中容易被忽略、但会直接破坏 Markdown 目录与锚点的重要问题。

典型异常：

- 程序打印内容中出现 `# Agent:`、`## Task:`、`## Thought:`；
- 提示词示例中出现 `# Role`、`## Instructions`；
- shell / 配置 / 文档示例中包含以 `#` 开头的字面文本；
- 代码围栏丢失或不配对，导致代码内部的 `##` 被渲染器识别为正文标题。

处理规则：

1. 先判断该段是否属于代码、终端输出、模型日志、提示词、JSON、配置或伪代码；
2. 如果属于上述内容，应使用完整、成对的 fenced code block 包裹，并尽量标记语言，如 `python`、`json`、`text`；
3. **代码块内部出现的 `# / ## / ###` 不得计入文档标题层级，也不得生成正文目录项；**
4. 对可执行代码中的注释符号 `#` 不要擅自改写；
5. 对纯“打印输出 / 日志展示”中仅用于视觉分级的 `# Agent:`、`## Task:`、`## Thought:` 等，可改成普通标签：`Agent:`、`Task:`、`Thought:`、`Using tool:`、`Tool Input:`、`Tool Output:`、`Final Answer:`；这样即使下游 Markdown 解析器处理不严谨，也不会误生成标题锚点；
6. 如果必须保留原始井号外观，而目标渲染器会误识别，可在**非可执行输出示例**中使用转义或等义形式（如 `\#\#`、`# #`），但不得修改真实代码语义；
7. 完成后必须检查所有代码围栏是否成对闭合。若示例内容本身包含三反引号，应使用更长围栏避免嵌套冲突。

### 6.1 修复代码块中的 OCR 错乱

如果 Markdown 代码块被 OCR、PDF 转换或其他流程破坏，必须优先恢复其可读性与基本结构，例如：

- 删除混入代码前的行号，如 `1`、`2`、`5`；
- 修复被错误拆开的 `import`、`def`、`class`、变量名、函数名和参数列表；
- 恢复下划线、括号、引号、逗号、冒号、缩进与代码围栏；
- 将被拆成多个围栏的同一段代码合并回一个连续代码块；
- 清理明显误识别的标识，如 `11m`、`preference agent`、`travel agent` 这类应为 `llm`、`preference_agent`、`travel_agent` 的代码变量写法。

处理原则：

- 只在上下文足以支持时恢复代码结构；
- 不凭空补完整业务逻辑，只修复明显的格式和语法层错误；
- 如果代码块本身只是示例代码，优先保证它“可读、连贯、结构正确”。

### 标题扫描必须忽略代码块

最终标题校验不能简单执行“查找所有以 `#` 开头的行”。正确逻辑是：

> 先识别 fenced code block 范围 → 排除代码块内部内容 → 再检查真正的 Markdown 标题。

## 7. 修复 Markdown 表格

检查所有表格是否存在：

- 列数不一致；
- 表头错位；
- 分隔线错误；
- 单元格内容被拆到表格外；
- 多余或缺失的 `|`；
- OCR 导致的错误换行；
- 无法正常渲染的结构。

可以在**不改变原始信息含义**的前提下修复表格。

如果内容明显原本就是表格，但转换后结构损坏，可以根据上下文恢复为合理 Markdown 表格。

不要为了美观而重写表格内容。

## 8. 清理 OCR / AI 转换异常

可以修复或删除：

- 明显乱码；
- 孤立无意义字符；
- OCR 错误符号；
- 明显错误的断词；
- 多余空格；
- 重复文字；
- 无意义数字或字母；
- 转换工具自动插入的辅助说明；
- 明显不是原书正文的 AI 转写提示。

但不要根据自己的知识擅自“纠正”作者观点或大幅修改原句。

# 四、页面杂质清理

## 9. 删除顶部目录

如果文档开头包含从原书、PDF、PPT 等提取出的目录页，可以删除顶部目录内容。

但必须注意：

- 保留书名；
- 保留副标题（如果它属于正式书名信息）；
- 不要误删真正正文；
- 只有在目录内容已由后文正文完整覆盖时才删除。

## 10. 删除页眉、页脚、页码和转换标记

删除明显不属于正文的内容，例如：

- 页眉；
- 页脚；
- 独立页码；
- 每页重复出现的书名；
- 每页重复的宣传文字；
- `<!-- page:24 -->` 等页面定位标记；
- `<!-- Image (...) -->` 等无实际正文意义的转换注释；
- PDF / PPT 转换工具生成的辅助说明。

但不要误删：

- 正文中的年份；
- 正常编号；
- 章节编号；
- 公式数字；
- 表格数据。

# 五、图片处理

## 11. 所有 Markdown 图片引用必须完整保留

例如：

```md
![第1页原始页面图](assets/page-001.png)
```

或：

```md
![](image.png)
```

或外部图片链接。

必须做到：

- 不删除；
- 不改名；
- 不修改路径；
- 不修改相对路径；
- 不替换图片；
- 不因为图片看起来重复就擅自删除。

处理完成后，应核对处理前后的图片引用数量和路径是否一致。

## 12. 区分“整页原始截图”和“正文插图”

### 整页原始截图

如果某张图片明显是当前页面的完整原始截图，而页面文字只是从该图片 OCR / AI 转写出来的，则页面顺序应调整为：

```text
标题
↓
整理后的可搜索正文文字
↓
原始页面图片
```

也就是：

> **标题 → 文字 → 页面原始图片**

不要继续保留：

> 标题 → 原始页面图片 → 文字

### 普通正文插图

如果图片本身属于正文中的具体位置，例如：

- 图表；
- 流程图；
- 示意图；
- 案例图片；
- 插画；
- 某一段文字直接对应的视觉内容；

则应尽量保持它与相关文字的原始位置关系，**不要统一移动到页面末尾**。

# 六、低频 / 特殊情况

以下规则只有检测到对应问题时才执行，不要为了套规则破坏正常文件。

## 1. 复杂图表或关系图页面

如果一页主要是：

- 流程图；
- 思维导图；
- 关系图；
- 复杂图表；
- 大量箭头与空间布局；

而 OCR 后的文字顺序明显混乱：

1. 尽量把可确定的文字关系整理成结构化 Markdown；
2. 保留原始页面图片；
3. 不要为了强制线性化而虚构关系；
4. 无法确定结构时，宁可少改，也不要凭空补充。

## 2. 无法确定是否属于正文的异常内容

如果某段文字看起来可能是：

- 页眉；
- 页面装饰；
- 图中标签；
- 正文；
- OCR 误识别；

且无法可靠判断，则优先保留，避免误删。

# 七、输出文件要求

## 13. 文件名直接使用真实书名

推荐命名示例：

```text
博弈论.md
```

不推荐命名示例：

```text
index.md
document-temp.md
博弈论——整理修正版.md
博弈论-最终版.md
博弈论-clean.md
```

不要在书名后附加：

- 整理版；
- 修正版；
- 最终版；
- fixed；
- clean；

等字符。

如果可以从正文中识别真实书名，应优先采用真实书名。

# 八、完成前的最终校验

输出前必须再完整检查一次：

1. 是否只有一个一级标题 `#`，并且它是书名；
2. 正文章节是否使用统一层级，书名与章节是否不同级；
3. CIP、出版信息、推荐序、序言、前言、作者/译者介绍等前置内容是否仍错误使用与正文章节相同的 `##`；
4. 是否先排除代码块后再检查标题，代码 / 日志 / 提示词里的 `#`、`##` 是否被误算为标题；
5. 所有 fenced code block 是否成对闭合，是否还存在会打断后续 Markdown 解析的代码围栏错误；
6. 是否仍存在 `## Task:`、`## Thought:`、`# Agent:` 等本应属于打印输出却会污染目录/锚点的伪标题；
7. 是否还有明显错误的标题层级；
8. 是否还有可以合理合并的“章节标题 + 页面主题”；
9. 是否存在明显标题跳级；
10. 是否仍有错误换行；
11. 列表缩进是否正常；
12. 表格是否可以正常渲染；
13. 是否仍残留页眉、页脚、页码；
14. 是否仍残留转换工具标记或 AI 辅助说明；
15. 繁体中文是否已经统一转换为简体中文；
16. 所有 Markdown 图片引用是否完整保留；
17. 图片路径是否完全没有修改；
18. 整页原始截图是否按“标题 → 文字 → 图片”排列；
19. 普通正文插图是否保持合理位置；
20. 是否误删、总结、压缩或改写了正文。

如果仍发现明显问题，应继续修复后再输出，而不是只处理最明显的几处。

# 九、完成后的回复内容

处理完成后，请告诉我：

- 修复了多少处标题层级；
- 前置内容（CIP、出版、推荐序、前言、作者等）是否已与正文章节层级分离；
- 清理了多少处代码 / 日志 / 提示词中的伪标题（如 `## Task:`）；
- 代码围栏是否全部成对闭合；
- 合并了多少处被拆开的页面标题；
- 是否修复了表格；
- 是否修复了错误换行和列表缩进；
- 是否清理了页眉、页脚、页码和转换标记；
- 是否执行了繁体中文 → 简体中文转换；
- 共保留多少条 Markdown 图片引用；
- 是否有任何图片引用被删除或修改；
- 当前整理后的正文文字字符数；
- 最终文件名。

正文字符数建议按：

> **排除 Markdown 格式符号、图片引用、HTML 注释和空白后的可见正文字符**

进行统计。

最后直接提供可下载的 `.md` 文件。

# 最重要的执行原则

> **一条规则只定义一次，特殊情况只补充例外，不重复定义通用规则。**

> **优先根据文档语义进行整理，而不是机械根据原 Markdown 标记修改。**

> **不改变正文含义，不删除图片引用，不因为修复一种文件的问题而给其他正常文件制造新问题。**
