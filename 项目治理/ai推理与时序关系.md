# AI 推理与时序关系

本文件约束 AI 怎样从人工表达形成项目对象，以及怎样避免把阅读顺序、执行顺序、依赖和因果混成一件事。

## 四类认知对象

| 类型 | 判断标准 | 允许的动作 | 禁止的动作 |
|---|---|---|---|
| Fact | 人明确表达或可由指定来源直接观察 | 保留原话、来源和当前承载 | 把 AI 解释写成人工事实 |
| Inference | AI 为组织、分类或补全逻辑而推导 | 标识推导、依据和待确认状态 | 直接升级为基线或机器契约 |
| Unknown | 当前证据不能确定 | 记录问题、影响、负责人和返回点 | 猜写、用旧实现填空或隐藏 |
| Conflict | 两个有效输入不能同时成立 | 保存双方、优先级依据和当前处理 | 静默删除一方或假装已经统一 |

“Fact”只说明人说过或来源显示过，不等于 C08 已完成人工决定，也不等于 C09 业务范围基线已经建立。

## 对象分类

AI 读取一段内容后，先判断它属于：

1. 业务目标、范围或需求；
2. 质量和验收约束；
3. 项目治理；
4. 候选方案或工程设计；
5. 机器投影和实现；
6. 运行状态和 Evidence；
7. 历史或已退役内容。

分类不确定时放入需求发现或推进问题清单，不为了找到“合适标题”而改变内容含义。

## 六种容易混淆的关系

| 关系 | 含义 | 例子 | 应保存的位置 |
|---|---|---|---|
| 阅读顺序 | 人怎样最容易理解文件 | 先项目说明，再需求，再治理 | README / 目录说明 |
| 需求形成顺序 | 语义怎样从原话到基线 | C01→C09 | 项目导航与阶段门 |
| 执行顺序 | 实际工作先做什么后做什么 | 页面阶段门、构建和运行 | 行为时序、工程任务、Workflow |
| 依赖关系 | 后项需要前项存在或通过 | C18 完整需求基线前不能做正式架构 | 阶段门、任务树 |
| 因果关系 | 一个事件导致状态变化 | 上游需求变化使 Verdict stale | 行为状态、变更治理 |
| 优先级 | 多项都可做时先处理什么 | 阻断型 Unknown 优先 | 问题清单、工作包 |

箭头只有在关系类型明确时才能使用。文件目录缩进只表示包含，不自动表示时间、依赖或因果。

## 推理步骤

```text
保留原始表达
→ 分句并标注来源
→ 分类为业务/治理/工程/运行/历史
→ 标识 Fact/Inference/Unknown/Conflict
→ 放入唯一职责文件
→ 检查是否产生了新语义
→ 人工确认后才升级生命周期
```

## 反方审计

每次形成框架或正文后，至少反问：

- 这个标题是否把实现手段伪装成业务目标？
- 这个编号是在帮助引用，还是迫使人工维护机器结构？
- 这个树是在组织已有对象，还是悄悄产生新对象？
- 这个箭头表示时间、依赖、因果还是仅仅阅读顺序？
- 这个答案来自人工、历史材料、AI 推导还是代码现状？
- 如果删掉 archive、YAML 和代码，当前业务文件是否仍能独立成立？
- 当前内容是否越过 C09、C18、C22 的相应基线或使用了未来证据？

任一项不能回答，就把结论降级为 Unknown/Conflict，并返回对应上游文件。

## 失败重入

| 失败类型 | 返回节点 |
|---|---|
| 原意或范围错误 | C01—C05 |
| 需求、场景或行为遗漏 | C06—C17 |
| 方案不支持需求 | C19—C24 |
| 追溯、Spec 或任务不闭合 | C25—C29 |
| 实现或测试失败 | C30—C34 |
| 运行结果与事前验收不符 | C35—C37 |
| Claim 超出证据或上游已变化 | C36—C40 |

重入只复用仍然有效的对象；被上游变化影响的下游必须标记 stale 或 invalidated，不能因节省时间而沿用。
