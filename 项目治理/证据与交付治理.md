# 证据与交付治理

本文件规定从真实受控运行到对外声明的最短可信链。它不定义业务验收内容；Acceptance 必须在运行前由需求阶段形成。

## 强制链路

```text
Controlled Run
→ Evidence
→ Independent Verdict
→ Delivery
→ Bounded Claim
```

任何节点缺失、失效或身份不一致，都不能绕过并继续形成下游结论。

## 对象职责

| 对象 | 只记录什么 | 不能证明什么 |
|---|---|---|
| Controlled Run | 已固定的来源、范围、版本、环境、配置和实际执行身份 | 不等于内容正确或已验收 |
| Evidence | 实际观察到的文件、内容、日志、截图、哈希和验证结果 | 不自行给出通过结论 |
| Independent Verdict | 对事前 Acceptance 与当前 Evidence 的独立判断 | 不扩张 Acceptance，也不代表所有场景 |
| Delivery | 引用有效 Verdict 的实际交付包及其边界 | 不代表通用能力或未来版本 |
| Bounded Claim | Evidence/Verdict 支持范围内的准确声明 | 不得声称未运行、未观察或未验收的能力 |

## 事前 Acceptance

- Acceptance 必须在 C17 形成，并在 C18 完整需求基线中得到人工确认。
- Verdict 必须逐条引用 Acceptance，不能在看见运行结果后修改判据以制造通过。
- 若 Acceptance 本身不完整，返回 C17 或 C18；不能用更多测试数量掩盖语义缺口。

## 哪些不是独立完成证据

- 文件或目录已经创建；
- 命令退出码为 0；
- 构建、静态检查、单元测试或 Contract 测试通过；
- HTTP 200、队列接受、PID 存在或 worker 已启动；
- 一次 Smoke、一个页面或一个代表样例成功；
- runner 自报 `passed`；
- 历史 Run、fixture、旧截图或过去的 95+ 评分。

这些可以成为 Evidence 的一部分，但不能单独形成业务 Verdict、Delivery 或 Claim。

## Evidence 最小身份

Evidence 至少能够解析到：来源指纹、处理范围、Run ID、代码/契约版本、环境、时间、实际观察、生成者和验证者。无法确定身份或混入其他来源时，标记不可用或 needs-review，不补写结论。

## 独立性

- 生成结果的执行器不能只凭自己的成功状态批准结果。
- Verdict 使用与执行分离的验证入口，并直接读取事前 Acceptance 和当前 Evidence。
- 人工抽查不能被伪装成全量 Verdict；自动测试也不能替代需要人工语义判断的 Acceptance。
- 发现验证器与被验证实现共享同一错误假设时，Verdict 必须降级并增加独立检查。

## 交付和声明边界

Delivery 只能引用当前有效 Verdict；Claim 必须注明来源、范围、版本、限制和未覆盖项。`needs-review` 或 `failed` 只允许作为证据保留，不得包装成完成交付。

## 新鲜度与失效

下列变化至少使相关 Evidence、Verdict、Delivery 和 Claim 进入 `stale` 或 `invalidated`：

- 来源文件、页码或候选关系变化；
- Requirement、Acceptance、架构、Spec、Workflow、Skill、Tool、Model 或实现变化；
- 运行环境或依赖变化到可能影响结果；
- Evidence 身份、哈希或完整性无法验证；
- 发现旧输出污染、漏页、错序或未声明的 Unknown。

恢复有效状态必须重新确定影响范围、重建、复测、生成新 Evidence 并取得新 Verdict；不得只改状态字段。
