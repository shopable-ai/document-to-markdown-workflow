# 项目分解与工作包

本文件说明怎样把大项目拆成可理解、可确认、可执行和可验收的小范围。它定义拆分方法，不提前创建当前尚未由 C22 架构基线授权的工程任务。

## 五种结构不能混用

| 结构 | 回答的问题 | 当前承载 |
|---|---|---|
| 项目分解 | 大项目包含哪些可独立负责的结果范围 | 本文件；必要时由项目说明引用 |
| 需求树 | 已有需求怎样按业务主题组织 | `项目需求/需求树.md` |
| 工程任务树 | 实现工作怎样拆分和依赖 | C22 架构基线后的 `工程执行/工程任务树.md` |
| Workflow 阶段图 | 运行时怎样流转、分支、失败和恢复 | C22 架构基线后的 Workflow 与人工说明 |
| 追溯图 | Requirement 怎样对应 Acceptance、Spec、Task、Evidence 和 Claim | `项目需求/需求到交付追溯.md` |

需求树不是任务树，目录树不是执行顺序，Workflow 也不产生业务需求。

## 从大项目到小范围

```text
项目目标与结束边界
→ 可独立判断价值的业务结果
→ 每个结果的输入、输出和边界
→ 场景、功能、行为与验收
→ C18 完整需求基线后的方案组件
→ C22 架构基线后的 Spec 和工作包
→ 可控制运行与证据
```

优先按“可独立验收的结果”拆分，不按目录、语言、模型、适配器或人员数量拆分。

## 子项目判定

只有同时满足下列大部分条件，才把范围提升为子项目：

- 有独立业务目标和结束边界；
- 有可单独确认的输入、输出、角色和验收；
- 可以独立排期、版本化、暂停或退役；
- 失败不会迫使其他范围共享同一运行状态；
- 需要独立的 Evidence、Verdict、Delivery 或 Claim。

只是一种文件格式、一个处理阶段、一个适配器或一个 Skill，通常是工作流分支或工程工作包，不自动成为子项目。

## 当前项目的候选结果分解

以下只用于检查需求覆盖，不是已批准工程任务：

| 结果范围 | 要回答的业务问题 | 当前去向 |
|---|---|---|
| 完整文档转换 | 用户指定范围怎样完整覆盖、保持页序并形成连续可用结果 | 目标范围、R01、R02、后续场景与验收 |
| 内容与结构转换 | 文字、数字、章节、层级、分区、列表和表格怎样忠实进入 Markdown | 需求、后续功能与行为 |
| 复杂视觉处理 | 哪些视觉需要可搜索表达与原图依据；裁剪必须保留哪些上下文 | 需求、U-B02、后续验收 |
| 读者包组织 | 输出根、文件名、资产相对路径、移动方式和覆盖策略是什么 | U-B01/U-B02、后续场景和设计 |
| 核对、拒绝与恢复 | 怎样发现错页、污染、Unknown、失败和中断；怎样返回修正 | 后续行为、状态、验收和运行控制 |

这些范围是否合并、拆分或成为独立工作包，要在 C09 业务范围基线和 C18 完整需求基线后根据场景和验收决定。

## 工作包最小框架

C22 架构基线后每个工程工作包至少需要：

1. 上游 Requirement、Acceptance 和 Spec；
2. 目标结果与明确不做；
3. 输入、输出、路径、命名和权限；
4. 前置条件、依赖和并行边界；
5. 正常、异常、恢复和停止行为；
6. 实现文件的允许修改范围；
7. 验证方法、通过条件和失败返回位置；
8. 需要保存的 Evidence；
9. 变更后应失效的下游对象；
10. 人工确认点和可声明范围。

## 拆分质量检查

- 每个范围是否能用一句话说清结果，而不是只说技术动作？
- 输入和输出是否明确且不与其他范围共享第二权威？
- 是否把一个业务需求错误拆成多个互相矛盾的实现任务？
- 是否存在太大的“完成全部转换”任务，无法独立验收或恢复？
- 是否存在太小的文件级任务，缺少用户可观察结果？
- 多文件、长任务、失败恢复和变更重测是否有独立边界？

任一项不能回答时，先回到目标、需求、场景或验收，不直接生成工程任务树。
